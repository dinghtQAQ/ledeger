# iOS 快捷指令记账需求草案

记录日期：2026-09-08  
状态：待确认，本文只记录需求与设计问题，不构成实现提交。

## 1. 目标

为现有个人总账增加一个 iOS 快捷指令入口，让用户在手机上快速记录两类账目：

- 收入（`income`）
- 普通支出（`expense`）

快捷指令应直接调用现有后端 API，不模拟点击网页前端。网页端继续作为完整的查询、分析、分类管理和冲正入口。

## 2. 明确不做的范围

- 不新增到期支出（`due_expense`）入口。
- 不在快捷指令中实现账目编辑、删除或冲正。
- 不在快捷指令中实现分析报表、账目分页查询或设置管理。
- 不把快捷指令做成独立 App。
- 本轮不修改代码，只确认需求、接口边界和实现难点。

## 3. 现有系统可复用的契约

创建账目使用：

```text
POST /entries
```

请求体的核心字段为：

```json
{
  "type": "income | expense",
  "amount": "十进制金额字符串",
  "occurredAt": "带时区的 ISO 8601 时间",
  "categoryId": 1,
  "subcategoryId": 2,
  "note": "可选备注"
}
```

规则：

- `amount` 必须是正数十进制字符串，业务精度最多四位小数。
- `expense` 必须提供粗分类 `categoryId`。
- `subcategoryId` 可为空，但如果提供，必须属于所选粗分类且处于启用状态。
- `income` 的分类字段可以为空。
- 每次请求必须携带唯一的 `Idempotency-Key`，以避免快捷指令重试造成重复记账。
- 账目发生时间默认应使用快捷指令运行时的当前时间；最终请求仍需携带明确的带时区时间。

## 4. 最小用户流程

推荐的首版快捷指令流程：

1. 选择“收入”或“支出”。
2. 输入金额。
3. 若选择“支出”，选择粗分类。
4. 可选选择细分类。
5. 可选输入备注。
6. 显示即将提交的摘要并请求确认。
7. 调用 `POST /entries`。
8. 根据 HTTP 状态显示成功、重复提交、鉴权失败或校验失败。

收入可以跳过分类步骤；支出不能跳过粗分类。快捷指令不应提供负数金额，方向由“收入/支出”选择决定。

## 5. 主要难点

### 5.1 鉴权方式是首要阻塞点

网页端当前主要使用 `HttpOnly`、`Secure` 会话 Cookie。快捷指令无法像网页一样自然复用浏览器的 HttpOnly 会话，也不应把网页登录密码或 Turnstile 流程硬编码进快捷指令。

后端当前还兼容 Bearer API key，但把长期生产 API key 放入 iPhone 快捷指令意味着：

- 快捷指令被导出、共享、同步或备份时可能泄露。
- 拥有该快捷指令的人可能直接写入整个账本，而不仅是调用“记账”界面。
- API key 一旦泄露，撤销和轮换需要额外运维动作。

因此，在开始实现前必须明确采用哪一种边界：

1. **个人低风险方案**：快捷指令保存 Bearer API key，接受密钥泄露风险。
2. **专用快捷指令凭据方案**：后端增加权限受限、可撤销、可轮换的写入令牌；快捷指令只持有该令牌。
3. **中转方案**：由 Mac 或其他自有服务保存真正密钥，手机快捷指令调用中转服务；这会增加部署和维护面。

现有同源 `Origin`/`Referer` 写请求校验也需要单独确认：来自 iOS 快捷指令的请求通常没有浏览器同源上下文，直接调用可能被现有安全边界拒绝。不能假设“有 Bearer key 就一定能写入”。

### 5.2 幂等键和重试

快捷指令可能因为网络超时而重试。若第一次请求已经被服务器接受、但手机没有收到响应，第二次请求必须复用同一个 `Idempotency-Key`，而不是重新生成，否则会产生两笔相同账目。

这要求快捷指令的重试流程明确保存本次操作的幂等键，并区分：

- 首次提交失败，可重新尝试。
- 服务端已接受但响应丢失，重复提交应得到原账目，而不是新账目。
- 同一个幂等键对应不同请求内容时，应提示冲突，不要静默覆盖。

### 5.3 分类输入体验

后端支出要求粗分类，但快捷指令本身不会自动知道当前启用的粗类和细类。若把分类名称硬编码在快捷指令中，会出现分类改名、停用或新增细类后不同步的问题。

候选做法：

- 首版只让快捷指令选择固定粗分类，细分类留给网页端补充。
- 快捷指令先调用 `GET /categories`，动态生成粗类和启用细类菜单。
- 快捷指令允许“未分类”，再由后端或网页端补录；这与当前“支出必须有粗分类”的契约冲突，不推荐。

推荐先动态读取分类；如果快捷指令平台的菜单表达能力或认证方式使动态读取过于复杂，再退回“固定粗类 + 可选细类”的窄方案，但需要记录同步责任。

### 5.4 时间与时区

快捷指令运行设备可能处于不同的时区。请求必须发送带时区的 `occurredAt`，不能只发送本地日期时间，也不能让服务端把无时区字符串猜成 UTC。

需要确定：

- 默认使用手机当前时间，还是让用户在快捷指令中选择发生时间。
- 用户人在旅行时，账目按手机当前时区记录，还是固定按账本时区记录。
- 快捷指令展示的时间是否需要在提交前确认。

推荐首版默认使用手机当前时间，并在确认摘要中显示本地时间；后端继续按现有 UTC 存储规则保存。

### 5.5 金额输入与确认

快捷指令的“询问输入”容易产生空字符串、千分位、货币符号或多余空格。首版需要在提交前做最小输入校验，并把金额按字符串传给 API，不能在快捷指令中用浮点数计算或改写金额。

对实际记账来说，确认步骤很有价值：它能降低把“支出”误选为“收入”、或把金额输错后直接写入不可编辑账本的风险。

### 5.6 移动网络下的错误反馈

快捷指令需要把 API 错误转换成用户能理解的短消息，至少覆盖：

- 未授权或凭据过期。
- 支出缺少粗分类。
- 细分类与粗分类不匹配或已停用。
- 幂等键冲突。
- 网络超时、服务不可用。

由于账本采用冲正而不是直接编辑，成功提交前的确认和失败后的明确反馈比网页表单更重要。

## 6. Mac 的作用

有 Mac 会降低制作和测试成本，但不会自动解决 iPhone 端的鉴权边界：

- 可使用 macOS“快捷指令”编辑器创建和调试快捷指令，再同步到 iPhone。
- 可在 Mac 上查看请求、测试 API、检查 JSON 和 HTTP 状态。
- 可用 Mac 运行本地开发服务或脚本，验证 `POST /entries`、幂等键和分类读取。
- 若选择中转服务，Mac 可以作为长期运行主机，但这会引入开机、网络可达性、证书和运维问题；不应把它当作默认前提。

因此，Mac 主要是开发/调试工具；快捷指令能否在离开家庭网络后稳定记账，仍取决于生产 API 地址、TLS、鉴权和网络可达性。

## 7. 建议的首版验收标准

- 能从 iPhone 选择收入或支出并完成一次真实 API 写入。
- 支出必须选择粗分类；收入可以不选分类。
- 金额和发生时间按 API 契约传递，不发生浮点改写或无时区时间。
- 网络超时后重试不会重复创建账目。
- 成功后能显示账目 ID、类型、金额和发生时间。
- 鉴权失败、分类校验失败和重复请求能给出明确提示。
- 快捷指令不包含网页登录密码。
- 快捷指令不提供到期支出、编辑、删除、冲正和分析入口。

## 8. 待确认决策树（第一轮）

### 第一轮结果（2026-09-08）

- **Q1 鉴权：已确认复用现有 Bearer API key。** 首版接受将 API key 保存在个人快捷指令中的风险；不新增专用令牌、中转服务或后端鉴权机制。
- **Q2 分类：已确认动态读取。** 快捷指令调用 `GET /categories`，根据当前返回的启用分类生成选择项。
- **Q3 提交确认：已确认需要。** 写入前显示类型、金额、分类、备注和发生时间，用户确认后才调用创建接口。
- **Q4 发生时间：已确认默认当前时间。** 首版不提供自定义发生时间入口。

### Q1：快捷指令如何鉴权？

**推荐：专用、可撤销、仅限记账写入的快捷指令令牌。** 这需要后端后续增加相应能力，但长期风险明显低于把主 API key 放进快捷指令。

备选：先用 Bearer API key 做个人内部原型，明确这是临时方案，并准备密钥轮换。

### Q2：首版是否动态读取分类？

**推荐：动态调用 `GET /categories`。** 这样快捷指令不需要维护一份会过期的分类列表。

备选：首版只固定七个粗分类，细分类不在快捷指令中选择。

### Q3：快捷指令是否每次提交前确认？

**推荐：确认。** 账目不可直接编辑，确认可以减少不可逆的录入错误。

备选：完全语音/一键快速写入，速度更快但误记风险更高。

### Q4：是否允许在快捷指令里填写发生时间？

**推荐：默认当前时间，首版不额外询问；需要补录历史账目时继续使用网页端。**

备选：增加“现在/自定义时间”分支，交互更完整但流程更长。

### 第二轮结果（2026-09-08）

- **Q5 API key 保存方式：已确认。** 导入快捷指令时记录现有 API key，快捷指令运行时读取该值；不在分享链接、二维码或公开文档中暴露。
- **Q6 分类读取失败：已确认采用降级提交。** 粗分类直接写死在快捷指令中；细分类优先调用 `GET /categories` 获取。如果接口无响应或读取失败，仍允许提交支出，但省略 `subcategoryId`。
- **Q7 收入分类：已确认跳过。** 收入不显示分类选择，支出才选择粗分类并尝试选择细分类。
- **Q8 成功提示：已确认采用推荐方案。** 显示“记账成功”、类型、金额、分类、发生时间和账目 ID，并提供复制账目 ID 的动作。
- **Q9 API 地址：已确认。** 快捷指令直接访问公网 HTTPS 生产地址，Mac 仅用于编辑和调试，不作为运行时中转。

### Q5：API key 放在哪里？

**推荐：作为快捷指令内部的私有文本输入保存，不在分享链接、二维码或公开文档中出现。** 需要换 key 时编辑快捷指令即可。

备选：每次运行时手动输入 key，安全性更高但失去快捷记账的便利。

### Q6：动态分类失败时怎么办？

**已确认方案：粗分类写死，细分类动态读取并允许降级。** 粗分类直接写入快捷指令；细分类通过 `GET /categories` 获取。如果接口未响应，仍提交支出，但不传 `subcategoryId`。后端仍负责校验粗分类有效性。

备选：分类读取失败就停止，不提交支出；或使用快捷指令内置的上次细分类缓存。两者均不是当前选择。

### Q7：收入是否显示分类选择？

**推荐：收入直接跳过分类；支出才读取并显示粗分类和可选细分类。** 这与现有领域规则一致，也能缩短收入录入流程。

备选：收入也显示分类菜单，保留未来扩展空间，但当前收入分类不是必填。

### Q8：提交成功后显示哪些结果？

**推荐：显示“记账成功”加类型、金额、分类、发生时间和账目 ID，并提供复制账目 ID 的动作。** 这样用户能确认服务器实际接受了哪一笔账。

备选：只显示成功提示，流程更短但不利于排查重复或误记。

### Q9：快捷指令从哪里访问 API？

**推荐：使用可从手机公网访问的 HTTPS 生产地址；Mac 仅用于编辑和调试，不作为运行时中转。**

备选：先连接家庭网络调用 Mac 或本地开发服务，仅适合原型测试，无法保证外出使用。

- **Q10 细分类选择：已确认提供“不选细分类”。** 这遵循现有 API 对可选 `subcategoryId` 的约定。
- **Q11 失败重试：已确认支持。** 网络失败或超时时允许重试，并复用同一个 `Idempotency-Key`；参数校验错误不自动重试。
- **Q12 粗分类维护：已确认写死且易维护。** 快捷指令首版内置当前七个固定粗分类；未来分类变化时手动同步这一处配置。
- **Q13 API key 更新：已确认集中配置。** API key 放在快捷指令开头的单一配置动作中，导入时填写，轮换时只修改该处。
- **Q14 语音输入：已确认暂不考虑。** 首版只使用文本输入和菜单选择。

### Q10：细分类菜单是否提供“不选细分类”？

**推荐：提供“不选细分类”选项。** 即使接口正常，用户也应能明确选择只记录粗分类；这与后端允许 `subcategoryId` 为空的契约一致。

### Q11：快捷指令是否支持失败后重试？

**推荐：支持一次“重试提交”，并复用同一个 `Idempotency-Key`。** 超时或网络失败时重试不会制造重复账目；明确的参数校验错误不应自动重试。

### Q12：粗分类写死后如何处理分类变更？

**推荐：首版按当前七个固定粗分类写死，并在文档中记录更新责任；后端粗分类发生变化时同步更新快捷指令。** 这是快捷指令简单可靠与分类自动同步之间的明确取舍。

### Q13：API key 更新如何操作？

**推荐：把 API key 集中放在快捷指令开头的配置动作中，导入时填写一次；轮换 key 时只修改这一处。** 不把 key 散落在多个请求动作里。

### Q14：快捷指令是否需要语音输入？

**推荐：首版使用系统文本输入和菜单选择，不专门设计自然语言解析。** 这样金额、类型和分类的输入边界更清楚，后续再考虑 Siri 语音优化。

## 11. 当前实现事实

当前实现事实：`POST /entries` 虽然支持 Bearer API key，但所有写请求仍要求 `Origin` 或 `Referer` 且必须通过同源校验；快捷指令若不带这两个请求头，当前实现会返回 `403`。因此，这不是快捷指令动作编排可以自行解决的问题，必须在实现阶段明确后端边界。

- **Q16 细分类选项：已确认。** 只显示当前粗分类下的启用细分类，并提供“不选细分类”。
- **Q17 幂等键：已确认。** 用户确认后、首次提交前生成；失败重试复用同一个键。
- **Q18 细分类超时：已确认。** 接口无响应时按无细分类继续提交。

### Q15：如何处理快捷指令请求的来源校验？

**安全复核中，暂未确认。** 为 Bearer API key 的快捷指令写入增加后端例外，可以解决 `Origin`/`Referer` 缺失导致的 `403`，但不会缩小现有 API key 的权限范围。当前 API key 仍可能访问其他业务接口，因此不能把“快捷指令内置确认”当作凭据安全措施。

现有风险：API key 被保存在快捷指令中，快捷指令被导出、共享、同步或备份时可能泄露；一旦泄露，攻击者可能绕过快捷指令直接调用 API。伪造固定 `Origin`/`Referer` 也不能解决这个问题。

候选方案：

1. **专用写入令牌（推荐生产方案）**：后端增加仅允许创建收入/普通支出的令牌，可撤销、可轮换，不允许查询、设置、冲正等其他操作。
2. **Mac 中转服务**：Mac 保存主 API key，快捷指令只调用受限中转接口；安全边界更清楚，但需要 Mac 持续运行、网络可达和额外维护。
3. **现有 API key + 快捷指令确认（临时原型）**：实现成本最低，但只能降低误记风险，不能降低 key 泄露后的权限风险。

### Q16：细分类接口只返回哪些选项？

**推荐：只显示当前选中粗分类下的启用细分类，并额外提供“不选细分类”。** 已停用细分类不进入新账目选择；接口失败时直接走无细分类降级。

备选：显示全部历史细分类，容易让用户选到已停用项并收到服务端错误。

### Q17：幂等键何时生成和保存？

**推荐：用户完成确认后、第一次发起 `POST /entries` 前生成一个随机幂等键；后续重试沿用该键，成功或明确失败后丢弃。** 不要在用户尚未确认时生成并复用旧键。

备选：快捷指令启动时生成幂等键，流程取消后可能留下难以理解的键生命周期。

### Q18：细分类读取超时阈值是多少？

**推荐：设置短超时；超时后立即按“无细分类”继续提交，不阻塞快速记账。** 具体秒数在实现规格中结合快捷指令动作能力确定。
